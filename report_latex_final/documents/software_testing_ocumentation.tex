\chapter{Software Testing Documentation}

\section{Scope of Testing}

\subsection{In-Scope Testing}

The test scope covers the main business functions of the Horse Racing Tournament Management System (HRTMS) web application. The purpose of testing is to verify that the core workflows work correctly for each role and that the backend data is stored and retrieved accurately.

\begin{itemize}
    \item \textbf{Authentication and Registration}
    \begin{itemize}
        \item Login with valid and invalid credentials.
        \item Login handling for locked accounts.
        \item Registration for Spectator, Horse Owner, Jockey, and Referee roles.
        \item Logout and redirect back to the login page.
    \end{itemize}

    \item \textbf{Admin and Tournament Management}
    \begin{itemize}
        \item Load, create, update, and delete tournaments.
        \item Create rounds and races.
        \item Assign referees and validate scheduling conflicts.
        \item Manage users, lock and unlock accounts, and change user roles.
        \item Approve, reject, and reset registrations.
        \item Manage prizes, awards, and tournament status.
    \end{itemize}

    \item \textbf{Horse Owner Workflow}
    \begin{itemize}
        \item Load, create, edit, and delete horse records.
        \item Validate horse age and other required fields.
        \item Select jockeys and send invitations.
        \item Register horses for tournaments.
        \item View registration status, profile details, upcoming races, and results.
    \end{itemize}

    \item \textbf{Jockey Workflow}
    \begin{itemize}
        \item View incoming invitations and respond with accept or reject.
        \item View schedule, profile, and awards.
        \item Update profile information.
        \item Validate profile rules such as unique email and required fields.
        \item Filter leaderboard data by tournament.
    \end{itemize}

    \item \textbf{Referee Workflow}
    \begin{itemize}
        \item View assigned races and race participant details.
        \item Inspect races and record draft results.
        \item Confirm official results.
        \item Report violations and validate fine amounts.
        \item Update result status from entered to completed.
    \end{itemize}

    \item \textbf{Spectator Workflow}
    \begin{itemize}
        \item Create, edit, and delete predictions.
        \item Lock predictions after race time.
        \item View upcoming schedules and completed race results.
        \item Update personal profile and spectator statistics.
        \item View leaderboard and filter by tournament.
    \end{itemize}

    \item \textbf{API Verification}
    \begin{itemize}
        \item Validate key backend endpoints with Postman.
        \item Verify user data, rankings, race lists, invitations, prizes, and race result APIs.
        \item Check response data, status codes, and persistence in the database.
    \end{itemize}
\end{itemize}

\subsection{Out-of-Scope Testing}

The following items are excluded from the final test scope because they are not part of the current release or they require a separate non-functional test plan:

\begin{itemize}
    \item External payment or betting integrations.
    \item Mobile application testing.
    \item Large-scale load or stress testing.
    \item Automated UI testing frameworks, because the team decided to use manual browser testing for UI verification.
    \item External services that are not implemented in the current HRTMS release.
\end{itemize}

\subsection{Constraints \& Assumptions}

\begin{itemize}
    \item Testing is performed in a production-like environment or a locally deployed environment with seeded test data.
    \item Test accounts for all roles are available before execution.
    \item Postman is used to verify backend endpoints and response payloads.
    \item UI verification is performed manually in the browser using the latest stable Chrome version.
    \item Test data is prepared in advance so that each role can follow its expected workflow without dependency issues.
    \item Database connectivity remains stable during the test window.
\end{itemize}

\section{Test Strategy}

\subsection{Testing Types}

This project uses three main testing types: Unit Testing, Integration Testing, and Functional Testing. The test strategy is built around manual UI verification and Postman-based API verification, which matches the final decision of the team.

\begin{itemize}
    \item \textbf{Unit Testing}
    \begin{itemize}
        \item \textbf{Objective:} Verify the correctness of individual functions, services, controllers, and validation rules in isolation. In HRTMS, unit-level checks focus on login logic, horse age validation, tournament registration rules, invitation validation, race result processing, and leaderboard calculation.
        \item \textbf{Technique:} White-box testing is applied by developers during implementation. Individual functions are checked with controlled inputs and mock data when they depend on the database or other modules.
        \item \textbf{Completion Criteria:}
        \begin{itemize}
            \item Core business logic in important modules is covered by unit checks.
            \item All unit test cases pass before code is merged.
            \item No critical logic defect remains in authentication, validation, or result processing.
        \end{itemize}
    \end{itemize}

    \item \textbf{Integration Testing}
    \begin{itemize}
        \item \textbf{Objective:} Validate that connected modules work correctly together, especially the interaction between the frontend, backend APIs, and database layer.
        \item \textbf{Technique:} Black-box and gray-box testing are performed with Postman and browser-based verification. API requests are sent to the backend, and the results are checked against expected database changes and screen behavior.
        \item \textbf{Completion Criteria:}
        \begin{itemize}
            \item All main integration scenarios are executed and passed.
            \item Data exchange between frontend, backend, and database is stable.
            \item No critical defect remains in login flow, registration, scheduling, invitation processing, or race result storage.
        \end{itemize}
    \end{itemize}

    \item \textbf{Functional Testing}
    \begin{itemize}
        \item \textbf{Objective:} Confirm that the implemented features satisfy the business requirements for each role in the system.
        \item \textbf{Technique:} Black-box testing is carried out manually through the browser to simulate real user journeys for Admin, Horse Owner, Jockey, Referee, and Spectator.
        \item \textbf{Completion Criteria:}
        \begin{itemize}
            \item All major functional requirements are covered by manual test cases.
            \item The tested features operate correctly for the intended role and screen.
            \item No blocking issue remains that prevents normal use of the system.
        \end{itemize}
    \end{itemize}
\end{itemize}

    \item \textbf{filterLeaderboardByTournament}: This case failed because the leaderboard filter did not return correct results in some scenarios.

\end{itemize}

The overall testing result shows that the system is stable for the main workflows. Most test cases passed successfully, and the remaining issues are concentrated in the Jockey workflow and one backend API case. These items should be retested after the related fixes and test data are prepared.
